## 2. 3 个"面试展开点"（简历写不下，面试用）

### 🎯 展开点 1：寄存器级外设驱动（最硬核）

**简历一句话**：寄存器级实现 USART / I2C / SPI，不依赖 HAL 库

**面试展开**：
- 直接读 RM0008 第 23/24/25 章
- 从 RCC_APBxENR 开时钟 → GPIO 配置 → 外设 CR1/CR2 → BRR/CCR/DR
- 72MHz 时钟树设计：HSE × 9 PLL → AHB /1 → APB1 /2 → APB2 /1
- **为什么不用 HAL**：HAL 移植性强但隐藏细节，面试官问"波特率怎么算"答不上来
- **产出**：5 个独立固件工程，每个 < 8KB

### 🎯 展开点 2：FreeRTOS 多任务设计

**简历一句话**：移植 FreeRTOS V10.6.1，4 任务 + 2 队列架构

**面试展开**：
- 为什么 RTOS：BNO055 100Hz 数据在裸机下丢 99%
- 任务优先级：Sensor (3) > Protocol (2) > TX (1) > Heartbeat (0)
- 队列长度计算：queue_data = 8（缓冲 80ms 突发）
- 抢占式调度 vs 时间片轮转
- **API 选择**：原生 FreeRTOS API（非 CMSIS-RTOS，面试官认可度更高）

### 🎯 展开点 3：自研通信协议 + 跨平台移植

**简历一句话**：自研二进制协议 + CRC16-MODBUS + 跨 STM32/ESP32 移植

**面试展开**：
- 帧格式设计：AA55 帧头 + LEN + TYPE + DST_ID + PAYLOAD + CRC16
- 字节序选择：大端（D3 决策，跨平台友好）
- CRC16-MODBUS：初值 0xFFFF，多项式 0xA001，通过 `123456789 → 0x4B37` 测试
- 跨平台策略：业务逻辑（nrf24.c）与硬件 SPI 分离
- **Python 验证工具**：tools/crc16_test.py，国际标准测试向量通过

## 3. 10 个高频面试 Q&A（必背）

### Q1: "你这个项目最大的技术挑战是什么？"

> **答**：BNO055 100Hz 数据采集在裸机下完全不可能（串行循环要 1000ms），必须用 RTOS 任务并行。
>
> 我设计了 4 任务架构：Sensor (prio 3) 每 10ms 采一次 BNO055 入队；Protocol (prio 2) 阻塞等队列打包成协议帧；TX (prio 1) 阻塞等 NRF24 发送。**通过优先级反转控制让高频数据绝不被协议打包阻塞**。
>
> 验证：串口日志显示 BNO055 数据流稳定 100Hz，队列占用率 < 50%。

### Q2: "为什么不用 HAL 库？"

> **答**：3 个原因：
> 1. **面试深度**：用 HAL 库调 API 答不出"波特率怎么算"，寄存器级能直接回答 USART_BRR = fck/(16×baud)
> 2. **代码体积**：寄存器级编译 < 8KB，HAL 库动辄 30KB+（虽然 F103 够大但是习惯要好）
> 3. **学习曲线**：把 RM0008 第 23-25 章读透，比调 HAL 函数更有竞争力

### Q3: "FreeRTOS 的任务调度机制说一下？"

> **答**：
> - **抢占式调度**（configUSE_PREEMPTION=1）：高优先级任务就绪时立即抢占 CPU
> - **时间片轮转**：同优先级任务轮流执行，每个时间片 = 1 个 tick
> - **调度触发点**：SysTick 中断（xPortSysTickHandler）+ PendSV 中断（上下文切换）
> - **优先级范围**：我们用了 0-4 共 5 个，configMAX_PRIORITIES=5
> - **关键点**：我们设 SysTick = 1kHz（每 1ms 一次），任务粒度 1ms

### Q4: "CRC16 怎么保证通信可靠？"

> **答**：CRC16-MODBUS 漏检率 1/65536 ≈ 0.0015%，比奇偶校验（50% 漏检率）强 3 万倍。
>
> **算法细节**：初值 0xFFFF，多项式 0xA001（反向 0x8005），每字节 XOR 后右移 8 次，遇 1 异或多项式。
>
> **验证方法**：用国际标准测试向量 "123456789" → CRC = 0x4B37，必须严格通过。我写了 Python 工具（`tools/crc16_test.py`）端到端验证。

### Q5: "为什么 NRF24 要选 2.4GHz 而不是别的频段？"

> **答**：
> - **频段优势**：2.4GHz ISM 频段全球免许可
> - **功耗**：NRF24 发射电流 11mA @ 0dBm，比 Sub-GHz 芯片便宜
> - **速率**：2Mbps 空中速率，32 字节包传输 < 1ms
> - **缺点**：和 WiFi 冲突，所以选信道 76（2476MHz）避开 WiFi 的 1/6/11
> - **替代方案**：Lora（远距离）、Zigbee（网状）都比 NRF24 复杂

### Q6: "FreeRTOS 中 ISR 和任务怎么通信？"

> **答**：必须用 **FromISR 结尾的函数**（如 `xQueueSendFromISR`）：
> 1. ISR 里不能阻塞，所以普通 API 不能用
> 2. `xQueueSendFromISR(queue, &item, &xHigherPriorityTaskWoken)` 第三个参数是"是否有高优先级任务被唤醒"
> 3. ISR 返回前调用 `portYIELD_FROM_ISR(xHigherPriorityTaskWoken)` 决定是否立即切任务
>
> **我们 v0.1 简化版**没用 ISR（用 `vTaskDelay` 轮询），v0.2 才上 ISR。

### Q7: "MQTT QoS 0/1/2 怎么选？"

> **答**：
> | QoS | 保证 | 场景 |
> |---|---|---|
> | 0 | 最多一次（可能丢）| 心跳、状态推送 |
> | 1 | 至少一次（可能重复）| 传感器数据 |
> | 2 | 恰好一次 | 计费、控制指令 |
>
> **我们选 QoS 1**：传感器数据**宁可重复不能丢**（重复了 OneNet Dashboard 自动覆盖），QoS 2 太重。

### Q8: "STM32F103 时钟怎么配置的？"

> **答**：72MHz 时钟树（RM0008 第 7 章）：
> ```
> HSE 8MHz → PLL × 9 → SYSCLK 72MHz
>                       ├─ AHB /1 → 72 MHz (CPU)
>                       ├─ APB1 /2 → 36 MHz (I2C, USART2/3)
>                       └─ APB2 /1 → 72 MHz (USART1, GPIO)
> ```
> **关键点**：
> - APB1 必须 /2（最高 36MHz）
> - Flash 必须开 2 个等待状态（48-72MHz）
> - 必须等 HSERDY + PLLRDY + SWS=PLL 三步验证
>
> 我写了 `firmware/common/system_stm32f1xx.c` 复用给 5 个工程。

### Q9: "项目里你遇到最大的 bug 是什么？怎么解决的？"

> **答**：I2C ACK 检测 bug。
>
> 我之前的代码用 RXNE 位判断 NACK（实际上 RXNE 是接收标志，跟 ACK 无关），导致 BNO055 应答失败时不会重试，**整个 I2C 通信静默失败**。
>
> **修复**：改用 SR1 寄存器的 AF 位（bit 10）判断 NACK，写 0 清 AF。
>
> **教训**：嵌入式调试核心心法是**永远读正确的状态寄存器**，不能"凑合"。

### Q10: "这个项目做完你最大的收获是什么？"

> **答**：3 点：
> 1. **系统思维**：从单片机裸机到 RTOS 多任务，再到跨平台协议，理解了"模块化 + 解耦"在嵌入式同样重要
> 2. **读手册能力**：RM0008 / NRF24 datasheet / FreeRTOS 官方文档，**手册>博客>猜测**
> 3. **工程化习惯**：每个 bug 都要有 commit、每个决策都要有 DECISIONS.md 记录

### 选项 A：时钟树 + 寄存器级驱动（5 分钟）

> "我所有 STM32 工程的时钟都是 72MHz，从 8MHz HSE 通过 PLL × 9 倍频得到。关键是 APB1 必须 /2 分频到 36MHz，Flash 必须开 2 个等待状态。这套配置我写成 `firmware/common/system_stm32f1xx.c` 复用给 5 个工程，每个工程 text 段都 < 8KB。"

### 选项 B：FreeRTOS 任务并行（5 分钟）

> "BNO055 100Hz 数据在裸机下根本采不到（串行循环周期 1 秒）。所以我用 FreeRTOS 做了 4 任务：Sensor (prio 3) 每 10ms 采一次 → 队列 → Protocol (prio 2) 打包 → TX (prio 1) 发送。**关键设计是优先级反转控制**：高频采集独占最高优先级，CPU 密集的 CRC16 计算被自动让位。"

### 选项 C：自研协议 + 跨平台（5 分钟）

> "我设计了一套二进制协议：AA55 帧头 + 长度 + 类型 + DST_ID + 载荷 + CRC16-MODBUS 校验。**算法部分**（CRC + 帧解析）和平台无关，所以 STM32 节点和 ESP32 网关共用一套代码。**我只换 SPI 收发函数**就完成了从 Cortex-M3 到 Xtensa 的移植。用 Python 工具验证过 `123456789 → 0x4B37` 标准测试向量。"
